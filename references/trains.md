# Verdesk — trains (record once, replay cheap) + objects + run

The first move of any multi-step task is **`suggest_macros()`**. A sequence that works becomes a **train** — the saved, self-verifying version you replay cheaply, even with a smaller model. A batch you didn't bother to save is `run_steps`.

## Gotchas (read first)
- **A replay failed.** → `playbook_replay` returns `{ok:false, failed_step, failed_tool, error, blackbox}`. Read it + open the `blackbox` PNG. A coord step that drifted → re-record or `playbook_edit_step`; prefer `click_button` objects for robustness.
- **`find_button` / `track_object` returns `{found:false}`.** → Not on this surface, off the viewport, or appearance changed past threshold. re-`look()`; `object_thumbnail` to recall its shape; relearn; or `click_text` if it has text.
- **`run_command` refused.** → The user turned off Settings → "Allow run_command" (it is ON by default): ask them to turn it on, or use `open_run` (visible).
- **A `(Pro)` tool errors on a free server.** → trains/objects/linked-objects need Pro. Basic see/click/read/run work in free.

## Batch a live sequence — `run_steps({steps:[{tool,args},…]})`
When you already know the exact mechanical steps AND the state they run in (fill these 4 fields, then click Submit), send them as ONE call instead of N round-trips. Verdesk runs them in order, reads each step's F1 outcome, and **STOPS at the first that didn't land** → `{ok:false, failed_step, tool, reason, result, results}` with that step's evidence + crosshair crop. All land → `{ok:true, executed, total, results}`. A successful batch is also recorded — you can `playbook_save` it. **Only batch deterministic steps inside a state you already see** — you can't batch across an unknown transition (page 2 of a wizard you haven't looked at). Supported tools: `navigate, browser_click, browser_fill, browser_type, browser_transfer, browser_get_value, browser_select_tab, browser_drag, press_key, type_text, scroll, wait, click_at, click_in_rect, click_text, drag_path, act_uia, focus_window, set_window_size, clipboard, set_view_target, run_command, click_button`. Any other tool (`open_run` included) is rejected with «not batchable via run_steps» — call it on its own.
**A person using the target stops the batch BEFORE the next input step** — `click_at`, `click_text`, `click_in_rect`, `click_button`, `type_text`, `press_key`, `drag_path`, `scroll`, and in the browser `browser_click`, `browser_type`, `browser_fill`, `browser_transfer`, `browser_drag` — with ``{ok:false, executed:i, failed_step:i, tool, reason:"Verdesk did NOTHING for `press_key`: since your last look the user clicked 3x…", result, results}`` and the fresh view attached. Steps before `i` already ran and are NOT undone: read the view and send the batch again FROM step `i`.

## Trains (Pro)
- `suggest_macros()` → trains whose recorded start-screen matches what's on screen NOW, closest first (`match_score` 0 = identical). Read-only. If one fits → `playbook_replay`; else do the task once → `playbook_save`.
- `playbook_record({task, description?})` — start, THEN do the task. Every mutating action is logged with its real delay. A `clipboard` WRITE is logged too, masked like `type_text` (a text that looks like a secret is saved as a `{secret_N}` variable, never its value); reading the clipboard is not.
- `playbook_save({validate?})` — persist after success; re-recording overwrites. `validate` (default TRUE) stores a photo of the final screen: only a replay whose final screen matches it earns reputation (`success_count`, `verified:true`). `validate:false` (for results that vary) never earns trust.
- `playbook_recall({task, include_steps?})` → the lightweight SIGNATURE (task, description, `params` = the function signature, objects, n_steps, total_ms, run_count, stars, validated, surface — NOT the steps); `include_steps:true` also returns the full steps + anchors. Exact-then-fuzzy match; does not execute. If no saved macro has that name, a draft of that name is returned.
- `playbook_list({scope?, status?})` → the CATALOG of signatures (never the steps), by last update — scan it before solving something from scratch. `scope` = a host (`sii.cl`; `mail.sii.cl` counts as `sii.cl`), a URL or an executable (`excel.exe`): only what belongs there, plus the drafts Verdesk auto-recorded there. `status` = `draft | tested | active | all`; without it, only the saved macros. An entry adds `status`, `not_replayable_steps`, `scope`, `agent` only when they apply. Verbs surface: `remember({op:"list", scope?, status?})`.
- `playbook_replay({task, args?, vault?, page?})` — runs a train server-side, honoring its delays; `args` fills the `{slots}`. **A slot you do not pass is not an error:** the run PAUSES and returns `{ok:true, paused:true, run_id, status:"paused", paused_by:"input", waiting:{slots:[{slot, kind:"secret"|"input", label, via:"vault"|"user", env, vault?}], control_port, run_no}}`. Give the values with `playbook_replay({run_id, inputs:{slot:"value"}})` (the user may type them in the run window instead); a `kind:"secret"` slot lives in memory only for the run and is masked everywhere. `vault:["secret_1"]` marks slots a vault bridge is filling (the call waits up to 120 s for them); `vault:[]` hands them back to the user.
  Control a live run with `playbook_replay({run_id, action:"pause"|"continue"|"stop"})`; `playbook_replay({run_id})` waits (≤30 s) and returns its state; `status()` carries `run` while one is alive. One run at a time; an idle pause stops itself after 15 min.
  A run stops only where it must. **Pause:** `paused_by` = `input` (a value is missing) | `anchor` (the click target is not where it was recorded: `paused_reason` = `anchor_mismatch` | `control_mismatch` | `control_unreadable`; `paused_detail` is free text, never parse it) | `user` | `ai` | `step` | `user_touched`; bring the screen back as recorded, then `action:"continue"` (it checks again) or `stop`. **Wait checks:** a `browser_wait_for` / `wait_for_uia` / `wait_until` step that times out STOPS the run (`stopped_by:"check"`, `check:{label, elapsed_ms, timeout_ms}`). **Failure:** `status:"failed"`, `error:{step, tool, message, reason}`; `reason` = `window_size` | `window_missing` | `app_unreadable` | `app_unverifiable` (the window can't be proven to be the recorded one) | `focus_failed` | `step_unverifiable` (a click with no recorded target: an old macro) | `anchor_mismatch`; the run window keeps a failed run up to 10 min and `playbook_replay({run_id})` returns it meanwhile. A step-by-step replay (`max_steps`) cannot pause: it fails with `stopped_by:"anchor"`. A desktop click or drag also needs the same CONTROL under the point it was recorded on.
  Before the first step the run puts the window back at its recorded size and in front; if the program is not open and the macro knows its `.exe`, it opens it (needs "Allow run_command"). **Fixing:** record again under the same name (`playbook_record` + `playbook_save` replaces it), or `playbook_edit_step` with `reanchor:true` (re-records that step's target from the CURRENT screen). A run paused on a click carries `repair_available:true`: the PERSON can press «Show where it is» in the run window — nothing for you to call. **Black box:** a PNG per input step under `<config>/verdesk/blackbox/<slug>/` (never sent to you, zero tokens); a failed step's result carries its `blackbox` path.
  A completed run answers `{ok:true, executed, total, params, success_count, stars, autonomy, recovered, verified?}`.
  Every final answer also carries `report:[{step, tool, ok, ms, result}]` — one entry per step, the same `result` a `run_steps` step gives (≤600 chars; `error` instead if the step failed), never the args; cite it to show which steps landed. A secret-slot step has `secret:true` and no result; a step that did not run is `{step, tool, ran:false}`. `playbook_replay({run_id})` returns it again for 10 min.
  Use `playbook_replay` for any saved train. The rest of its behavior (the up-front health check, how macros recorded before 2.61.0 prove their window, every code) is in the `playbook_replay` tool description: read it when a run stops for a reason not listed here.
- **Already typed on the page — `page`:** `playbook_replay({run_id, page:{slot:true}})` (also with `task` at start) tells the run the person already typed `slot` on the page or app: it neither asks for it nor stores it. ONE mark = ONE use: the run SKIPS the step that only types that slot (`type_text` / `browser_type` / `browser_fill` whose text is exactly `{slot}`, no `submit:true`); a LATER step that types it pauses again. A step that uses the slot any other way is not skipped: the run pauses with `paused_reason:"on_page_not_skippable"` (`paused_detail` says why). `page:{slot:false}` undoes a mark. `waiting.slots[i]` carries `on_page`, `on_page_refused` (the mark was just spent) and `vault_failed`. Refused: `slot_via_vault`, `bad_page`. A value and a mark for the same slot in one call → the value wins. Over HTTP: `POST /control/replay/input {run_id, inputs?, page}`. Use it when the person says they already typed a value on the page; the rest is in the `playbook_replay` tool description.
- **Remember a password — `remember`:** `playbook_replay({run_id, inputs:{secret_1:"…"}, remember:{secret_1:true}})` (also with `task` + `args` at start, or `POST /control/replay/input {run_id, inputs, remember}`) saves the value of a SECRET slot, given in THAT same call, encrypted for this Windows user (never in the macro, an export, a log or a result). Later runs type it by themselves — only for the same macro, slot and place (the site's host or the program's exe); deleting or re-recording the macro forgets it. It goes by itself only if the previous run that used it was CONFIRMED (ended well and the screen where it was typed no longer exists); otherwise the next run asks again with `waiting.slots[i].remembered_rejected:true`, and what you give then replaces it. `remember:{slot:false}` forgets it. `waiting.slots[i]` carries `can_remember` and `remember_store`; the run state carries `remembered:{used,saved,failed}`. Errors: `remember_needs_value`, `remember_not_secret`, `remember_unavailable`, `bad_remember`. Do not ask the person again after the first run.
- **Literal braces.** `{name}` in a step's text is a slot. To type a literal `{`, write `{{` (`{{secret_2}` types «{secret_2}»); a `}` never needs escaping. The recorder does it for you: text you typed while recording is saved with its `{` doubled, so it never becomes a slot of the macro, and the replay types it as you wrote it.
- `playbook_set_delays({task, delays?|uniform_ms?|scale?})` · `playbook_edit_step({task, step, args?, delay_before_ms?, tool?, reanchor?})` (edit one 0-based step in place; `reanchor:true` re-records its target from the current screen) · `playbook_annotate({task, notes?:[{step, note}], vault?:{slot:{module_id, line?}}})` (`vault` stores the LINK of a `{slot}` to a CleverCoder vault block — module and line, never the value; `null` removes it) · `playbook_delete({task})`.
- **Autonomy (supervised → trusted):** each train carries `success_count`, `stars` (0-5), `autonomy` (`supervised`|`trusted`), `reversibility` (`read_only`|`benign`|`mutating`|`irreversible`). Fresh = supervised (watch it). ≥3 photo-verified runs → trusted (unattended). A trusted train that breaks drifts back to supervised until repaired. Give even a trusted train a look before an `irreversible` step (a `run_command` can't be undone).
- **Self-healing:** a train carries `healthy` + `last_failure`. A failed step is RECORDED on the train (the catalog shows "broken at step N" without re-running). Loop: replay → break → SEE it (the `blackbox` path) → repair (`playbook_edit_step`/objects) → replay; a clean run sets `recovered:true`.

## Vault bridge — a secret from the CleverCoder vault reaches the run without passing through you
1. `playbook_replay({task})` WITHOUT the secret → it pauses. Each `waiting.slots[i]` has `env` (e.g. `VERDESK_SECRET_1_PASSWORD`) and, if the macro was linked, `vault:{module_id, line, env:[{name, module_id, line}]}` — that `env` goes to `vault_run` as is. `waiting.control_port` and `waiting.run_no` are the script's two arguments (both numeric).
2. Not linked? `vault_list` → pick the block → `playbook_annotate({task, vault:{secret_1:{module_id, line}}})` once. It saves WHERE the value is, never the value; a link that stops existing (vault changed, other project) just makes `vault_run` say so.
3. `playbook_replay({run_id, vault:["secret_1"]})` — returns at once; the run window says "asked the vault" and shows no field. `vault:[]` gives the slots back to the user (do it if `vault_run` fails).
4. `vault_run({script:"scripts/verdesk-vault-bridge.ps1", args:["<control_port>","<run_no>"], env:[…the vault.env of every waiting slot…], timeout_sec:120})` → `run_id`; follow with `vault_run_status`. The script POSTs the values, with the run number, to `127.0.0.1:<control_port>/control/replay/input` (loopback only, not MCP: nothing in the JSON-RPC, no «in use by» notice) and prints ONE status line, never a value. When nothing is missing the run goes on by itself. A late delivery (the user took long to approve the script) still fills the SAME run while it waits for the slot; if that run was stopped and another one started, Verdesk refuses it (`not_active`) and nothing is typed anywhere.
5. Exit codes: 0 delivered (the line says `filled` and `still missing`: a field the user must type is not an error); 2 no port, no run number or no `VERDESK_*` variable; 3 Verdesk did not answer; 4 Verdesk refused (`no_run`, `not_active`, `unknown_slot`, `too_long`). Do not loop: read the line, then `playbook_replay({run_id})`.

Write this file once, EXACTLY (PowerShell 7, UTF-8 without BOM; `vault_run` only runs project scripts and the user approves it once in CleverCoder):

```powershell
# scripts/verdesk-vault-bridge.ps1 - run by vault_run with args = [Verdesk control port, run number] and VERDESK_<SLOT>_<PASSWORD|USER|...>
# variables in its environment. Hands them to the macro run that asked for them (run number), never to another. Talks only to 127.0.0.1; never prints a value.
$ErrorActionPreference = 'Stop'
if ($args.Count -lt 2 -or $args[0] -notmatch '^[0-9]{2,5}$' -or $args[1] -notmatch '^[0-9]{1,18}$') { Write-Output 'missing control port or run number (two numeric arguments)'; exit 2 }
$inputs = @{}
foreach ($v in Get-ChildItem Env:) { if ($v.Name -match '^VERDESK_(.+)_(PASSWORD|USER|USERNAME|TOKEN|KEY|SECRET)$') { $inputs[$Matches[1]] = $v.Value } }
if ($inputs.Count -eq 0) { Write-Output 'no VERDESK_* variable arrived'; exit 2 }
$body = @{ run_no = [int64]$args[1]; inputs = $inputs } | ConvertTo-Json -Compress
try {
    $r = Invoke-WebRequest -Uri "http://127.0.0.1:$($args[0])/control/replay/input" -Method Post -ContentType 'application/json; charset=utf-8' `
        -Body ([Text.Encoding]::UTF8.GetBytes($body)) -UseBasicParsing -TimeoutSec 30 -SkipHttpErrorCheck
} catch { Write-Output ('Verdesk did not answer: ' + $_.Exception.Message.Split("`n")[0]); exit 3 }
$j = $null
try { $j = [string]$r.Content | ConvertFrom-Json } catch { }
if ($r.StatusCode -ge 400 -or $null -eq $j -or $j.ok -ne $true) {
    $why = if ($j -and $j.error) { [string]$j.error + $(if ($j.slot) { ' ' + [string]$j.slot } else { '' }) } else { 'HTTP ' + [int]$r.StatusCode }
    Write-Output ('Verdesk refused: ' + $why); exit 4
}
Write-Output ('filled: ' + (@($j.filled) -join ',') + '; still missing: ' + $(if (@($j.still_missing).Count) { @($j.still_missing) -join ',' } else { 'none' }))
exit 0
```

## Drafts (Pro) — what Verdesk recorded on its own
While you work through Verdesk tools it keeps a **draft** of your route per site/app and agent. It closes when the site/app changes, after 600 s without actions, or at 200 steps (under 2 steps is discarded). Pro only, and only while the user has not switched recording off. It never records the user's own keyboard or mouse — only calls made through Verdesk tools. Drafts stay on this computer; the user reviews and deletes them in the app's Macros tab.
- **Find them.** Arriving at a site/app (after `navigate`, `go`, `set_view_target`, `focus_window` or `browser_select_tab`) Verdesk appends ONE line to the response — once per agent + scope per server session, nothing if there are none: `Verdesk: 2 drafts + 1 macro for sii.cl - playbook_list({scope:"sii.cl"})` (verbs surface: `remember({op:"list",scope:"sii.cl"})`). Read one with `playbook_recall({task, include_steps:true})`.
- **A draft is a guide, not a macro.** `status:"draft"` = not yet reviewed, not replayable until promoted. A step with `not_replayable:true` uses a tool the replay does not repeat yet (`navigate`, `browser_fill`, `browser_transfer`…): a replay would STOP there; the signature's `not_replayable_steps` counts them. A step may carry a `locator` (url, title, process, `dom` {selector, role, name, context, text}, `uia`, text_around, `rel`, `crop`) — the signals to find its target again.
- **Secrets are never stored.** A value Verdesk recognizes as a secret is replaced by `{secret_N}` and the step has `secret:true` (no crop, no nearby text); in a draft, a field it cannot classify is masked too. Detection outside password fields is best effort: do not type a secret you would not want near a draft.

## Objects — the Pixel Match book (Pro)
Teach a button by its pixel fingerprint and re-find it anywhere — works where UIA falls short (games, custom UIs, WebView).
- `learn_button({label, x, y, w, h, app?})` — fingerprint a bbox (errors on a uniform region — include the glyph).
- `find_button({label})` → `{found, x, y, rect, match_pct, candidates}` or `{found:false}`.
- `click_button({label})` — find + click; the visual action recorded by trains. On replay it resolves the object by its EXACT recorded name (a renamed/deleted object fails the step instead of clicking a lookalike). It clicks only when ONE place wins clearly: two places that match about equally end in an `ambiguous` error listing them, with no click — and the object's backup images (variants) all count, so two copies that look different (one per theme, say) are still two places. `find_button` only reports the first fingerprint that matches, so it can show one candidate where `click_button` says ambiguous.
- `track_object({label})` → `{found, moved, dx, dy, searched}`. `object_thumbnail({label})` → 48px sample. `list_buttons()` · `delete_button({label})`.

## Linked objects (Pro)
Deterministic analysis of `playbooks.json` + `buttons.json` (no screenshot/model).
- `object_links()` → `{objects:[{label, registered?, app, trains, last_seen_rect}], orphan_refs, unused}`.
- `objects_used_by_train({task})` → objects a train links to. `trains_using_object({label})` → trains linking an object (move/relearn one → see the N affected).

## Run commands on the machine (two distinct tools)
- `open_run({command})` — opens the OS Run dialog (Win+R), types, Enter. **Visible, OS-mediated; desktop target only** (on the browser it answers `error_type:"wrong_target"` and sends no keys). For GUI apps (`mspaint`), terminals (`cmd`/`powershell`/`wt`), or a `cmd /c …` one-liner that closes itself. After opening a terminal, drive it: `type_text` + `press_key({key:"Enter"})`.
- `run_command({command, cwd?, detach?, timeout_ms?})` — runs **locally** via `cmd /C`, captures `{stdout, stderr, exit_code, timed_out, duration_ms}` (`timeout_ms` default 30000). `detach:true` launches a GUI/long-running process and returns at once without capturing. **ON by default**; refuses with an error if the user turned off Settings → "Allow run_command". For trains it's classified `irreversible` — a command can't be undone.
