# Verdesk — macros (trains): record once, replay cheap

A **macro** (the tools call it a train or playbook) is a sequence you did once and Verdesk saved, so it can repeat it with its own checks, even with a smaller model. It is how a person automates their own routine on their own accounts: opening a portal, filling a form, posting a photo. Macros, saved buttons and objects are Pro: on a free server those tools answer that they require Verdesk Pro, and `look`, `click_text` and `read_text` keep working.

## 1. The short path
1. `suggest_macros()` → the macros whose recorded start-screen matches the screen now, closest first (`match_score` 0 = identical). Read-only.
2. One fits → `playbook_replay({task, args?})`.
3. None fits → `playbook_record({task})`, do the task once, `playbook_save()`. Next time, step 2.
4. A run that stops says what it needs (a value, the screen as it was recorded): section 6.

## 2. One-off batch — `run_steps({steps:[{tool,args},…]})`
When you already know the exact steps and the state they run in (fill these 4 fields, then click Submit), send them as one call. Verdesk runs them in order, reads each step's outcome and stops at the first that did not land → `{ok:false, failed_step, tool, reason, result, results}` with that step's evidence. All land → `{ok:true, executed, total, results}`; the batch is also recorded, so `playbook_save` can keep it. Batch steps inside a state you already see, not across a screen you have not looked at. Supported tools: `navigate, browser_click, browser_fill, browser_type, browser_transfer, browser_get_value, browser_select_tab, browser_drag, press_key, type_text, scroll, wait, click_at, click_in_rect, click_in_cell, click_text, drag_path, act_uia, focus_window, set_window_size, clipboard, set_view_target, run_command, click_button`. Any other tool (`open_run` included) answers `tool «open_run» is not batchable via run_steps (not a supported deterministic action)`: call it on its own.
When the person uses the target meanwhile, the batch stops before the next input step (`click_at`, `click_text`, `click_in_rect`, `click_button`, `type_text`, `press_key`, `drag_path`, `scroll`, and in the browser `browser_click`, `browser_type`, `browser_fill`, `browser_transfer`, `browser_drag`) with `{ok:false, executed:i, failed_step:i, tool, reason:"…since your last look the user clicked 3x…", result, results}` and the fresh view attached. Steps before `i` already ran: read the view and send the batch again from step `i`.

## 3. Find a macro
- `suggest_macros()` — see section 1.
- `playbook_list({scope?, status?})` → the catalog of signatures (never the steps), by last update: scan it before solving something from scratch. `scope` = a host (`sii.cl`; `mail.sii.cl` counts as `sii.cl`), a URL or an executable (`excel.exe`): only what belongs there, plus the drafts Verdesk recorded there. `status` = `draft | tested | active | all`; without it, only the saved macros. An entry adds `status`, `not_replayable_steps`, `scope`, `agent` only when they apply. On the verbs surface (the six-verb catalog in SKILL.md): `remember({op:"list", scope?, status?})`.
- `playbook_recall({task, include_steps?})` → the SIGNATURE (task, description, `params` = the slots it takes, objects, n_steps, total_ms, run_count, stars, validated, surface; not the steps); `include_steps:true` adds the steps and anchors. Exact match, then fuzzy; it does not run anything. If no saved macro has that name, a draft of that name is returned.

## 4. Record and save
- `playbook_record({task, description?})` — start, then do the task. Every action that changes something is logged with its real delay. A `clipboard` write is logged too, masked like `type_text` (a text that looks like a private value is saved as a `{secret_N}` variable, not as itself); reading the clipboard is not logged.
- **In the Verdesk browser (preferred)** (`set_view_target("browser")`) a recording keeps `navigate`, `browser_click`, `browser_fill`, `browser_type` and `browser_transfer`, and a replay repeats them by the element: it finds it again on the page by its selector, role and name — not by the `@eN` reference from `browser_snapshot` it was recorded with —, waits up to 8 s for it to appear, and pauses (`paused_reason:"anchor_mismatch"`) if it is missing or more than one element matches. A step whose element could not be located is recorded the older way (a pixel `click_at`, or `type_text` after a click on the field).
- `browser_snapshot` and `browser_describe` show an element's role, name and text, not a stable selector, and neither acts; `browser_click` always does (no tool previews a click). A step you record keeps the element's selector, role and name by itself.
- **Any other browser window, as a desktop target:** a replay repeats `run_command`, `set_view_target`, `focus_window`, `click_text`, `click_in_rect`, `type_text`, `press_key` and `wait_until`; the `browser_*` tools exist only in the Verdesk browser.
- `playbook_save({validate?})` — keep it after a success; recording again under the same name replaces it. `validate` (default true) stores a photo of the final screen: only a replay whose final screen matches it earns reputation (`success_count`, `verified:true`). `validate:false` (for results that vary) never earns it.
- **Literal braces.** `{name}` in a step's text is a slot. To type a literal `{`, write `{{` (`{{secret_2}` types «{secret_2}»); a `}` needs no escape. The recorder does this for you: text typed while recording is saved with its `{` doubled.
- **Edit a saved macro:** `playbook_edit_step({task, step, args?, delay_before_ms?, tool?, reanchor?})` (one 0-based step, in place; `reanchor:true` re-records its target from the current screen) · `playbook_set_delays({task, delays?|uniform_ms?|scale?})` · `playbook_annotate({task, notes?:[{step, note}], vault?:{slot:{module_id, line?}}})` (`vault` links a `{slot}` to a CleverCoder vault block — module and line, not the value; `null` removes the link) · `playbook_delete({task})`. No tool adds or removes a single step: record the macro again, or the person edits it in the Macros tab.

## 5. Run with arguments — `playbook_replay({task, args?, vault?, page?, remember?})`
It runs the macro server-side, honoring its recorded delays. `args` fills its `{slots}`, so one macro serves many runs: «post this photo with this text» → `playbook_replay({task:"reddit post", args:{subreddit:"3Dprinting", title:"My first print", body:"Printed in PETG", image:"C:\\photos\\part.jpg"}})`. `playbook_recall` lists the slots (`params`).
- **A slot you leave out is not an error:** the run pauses and returns `{ok:true, paused:true, run_id, status:"paused", paused_by:"input", waiting:{slots:[{slot, kind:"secret"|"input", label, via:"vault"|"user", env, vault?}], control_port, run_no}}`. Give the values with `playbook_replay({run_id, inputs:{slot:"value"}})`, or the person types them in the run window. A `kind:"secret"` slot lives in memory only for the run and is masked everywhere.
- **Control a live run:** `playbook_replay({run_id, action:"pause"|"continue"|"stop"})`; `playbook_replay({run_id})` waits (≤30 s) and returns its state; `status()` carries `run` while one is alive. One run at a time; an idle pause ends by itself after 15 min.
- **Before the first step** the run puts the window back at its recorded size and in front; if the program is not open and the macro knows its `.exe`, it opens it (needs Settings → "Allow run_command", on by default).
- **A finished run** answers `{ok:true, executed, total, params, success_count, stars, autonomy, recovered, verified?}` and `report:[{step, tool, ok, ms, result}]` — one entry per step, the same `result` a `run_steps` step gives (≤600 chars; `error` instead if the step failed; never the args); cite it to show which steps landed. A step that typed a secret slot has `secret:true` and no result; a step that did not run is `{step, tool, ran:false}`. `playbook_replay({run_id})` returns it again for 10 min.

## 6. Pauses, failures and repair
A run stops only where it must, and says why.
- **Pause** (`paused_by`): `input` (a value is missing) · `anchor` (the click target is not where it was recorded; in the browser, the element is missing, several match, or the recorded step has no role, name or context to tell it apart: `paused_reason` = `anchor_mismatch` | `control_mismatch` | `control_unreadable`; `paused_detail` is free text, do not parse it) · `user` · `ai` · `step` · `user_touched`. Bring the screen back as recorded, then `action:"continue"` (it checks again) or `stop`. A run paused on a click carries `repair_available:true`: the person can press «Show where it is» in the run window and click the right place — nothing for you to call.
- **Wait checks:** a `browser_wait_for` / `wait_for_uia` / `wait_until` step that times out ends the run (`stopped_by:"check"`, `check:{label, elapsed_ms, timeout_ms}`).
- **Failure:** `status:"failed"`, `error:{step, tool, message, reason}`; `reason` = `window_size` | `window_missing` | `app_unreadable` | `app_unverifiable` (the window cannot be shown to be the recorded one) | `focus_failed` | `step_unverifiable` (a click with no recorded target: an old macro) | `anchor_mismatch`. The run window keeps a failed run up to 10 min and `playbook_replay({run_id})` returns it meanwhile. A desktop click or drag also needs the same control under the point it was recorded on.
- **Repair:** record again under the same name (`playbook_record` + `playbook_save` replaces it), or `playbook_edit_step` with `reanchor:true` (click and drag steps). A browser step is repaired on the page: open the page it expects and `action:"continue"`, and it looks for the element again; `playbook_edit_step` changes its arguments (a slot, a delay) but the element it looks for comes from the step's recorded locator, which stays as it is, and `reanchor` does not apply to it — when the site itself changed, record the macro again. Loop: replay → pause or failure → look at it (a failed step's result carries its `blackbox` path: a PNG per input step under `<config>/verdesk/blackbox/<slug>/`, never sent to you, zero tokens) → repair → replay; a clean run sets `recovered:true`. A train carries `healthy` and `last_failure`, so the catalog shows «broken at step N» without running it.
- **Trust grows with use:** each macro carries `success_count`, `stars` (0-5), `autonomy` (`supervised` → `trusted` after ≥3 photo-verified runs; a trusted macro that breaks goes back to supervised until repaired) and `reversibility` (`read_only`|`benign`|`mutating`|`irreversible`). Give even a trusted macro a look before an `irreversible` step (a `run_command` cannot be undone).
- Everything else (the health check before the first step, how macros recorded before 2.61.0 prove their window, every code) is in the `playbook_replay` tool description.

## 7. Private values and sign-in
Signing in is a normal macro step, the same for a bank, a tax portal or a mailbox, and it is the person's own account. The macro carries the password as a variable: a `{name}` slot whose name says it is private: it starts with `secret_`, or has one of the words password, pass, pin, token, secret, clave, contrasena, cvv, otp, 2fa or mfa (a whole word: `{user_password}`, `{miClave}`). Each run fills it in one of three ways, from most to least hands-off:
- **CleverCoder vault** — the value is read by name from the person's own vault and nobody types it, which is safer than typing by hand. Link the slot once with `playbook_annotate({task, vault:{password:{module_id, line}}})`; a run you start with `playbook_replay` then takes the value through the Vault bridge (section 8) without passing through you. A run the person starts with ▶ in the Macros tab does not use the vault: its run window asks for the value, or «Remember password» fills it.
- **«Remember password»** — the person types it once in the run window and ticks that box; Verdesk keeps it encrypted for their Windows user and later runs sign in by themselves. Re-recording or deleting the macro forgets it.
- **The run window** — the person types it each time, or signs in on the page and clicks «I already typed it on the page».
If the person hands you the value in the conversation, pass it once with `inputs` + `remember` (below) and do not repeat it.

**Record a login in the Verdesk browser:** `playbook_record({task:"tax-login"})`, `navigate` to the login page, `browser_snapshot`, `browser_fill` the user name as it is and `browser_fill` a placeholder (`x`) at the password field — `browser_fill` replaces what the browser may have autofilled; the real value stays out of the recording, and a field Verdesk recognises as a password is saved as `{secret_1}` by itself. Before the sign-in click, ask the person to type their real password on the page (that typing is not recorded), so the site never receives the placeholder; then `browser_click` the sign-in button, `browser_wait_for` the signed-in page and `playbook_save`. Then turn typed values into slots (step 3 below). From the first run on, the run window asks for the password, or the vault fills it.

**Record it on another browser window (a desktop target):**
1. `playbook_record({task:"tax-login"})`. Open the page: `run_command({command:'start "" "https://…/login"', detach:true})`, then `set_view_target` to that window, `focus_window({hwnd_hex})` and `wait_until({label:"<a control of the form>", state:"visible"})` (on a desktop target `wait_until` waits for a control, not for text).
2. Click the field, then `type_text`: `click_in_rect` on the field, or `click_text` on its label with more words (a lone word like «RUT» may match the address bar, where it is part of the URL, and focus that instead). Type the user name as it is; at the password field type a placeholder (`x`) and, before `press_key` Enter, ask the person to type their real password on the window (not recorded), so the site never receives the placeholder. `press_key` Enter, `wait_until` a control of the signed-in page, `playbook_save`.
3. Turn typed values into slots with `playbook_edit_step({task, step, args:{text:"{password}"}})` — `step` is the 0-based position in `playbook_recall({task, include_steps:true})`. Do the same for a value that changes between runs (`{rut}`, `{user}`). Recall again to check each step reads its slot (a field Windows marks as a password may already read `{secret_1}`). `args` replaces the step's whole args: keep its other fields — for a `browser_fill` step, `args:{target:"#password", value:"{password}"}`.
4. Run it: `playbook_replay({task, args:{rut:"12.345.678-9"}})`, or the person presses ▶ in the Macros tab of the Verdesk app. A slot with no value pauses the run (`paused_by:"input"`) and the run window asks for it; tell the person in one line: «Verdesk's window is asking for your password — type it there and tick "Remember password", or sign in on the page and click "I already typed it on the page".»

**Already typed on the page — `page`:** `playbook_replay({run_id, page:{slot:true}})` (also with `task` at start) tells the run the person already typed `slot` on the page or app: it neither asks for it nor stores it. One mark = one use: the run skips the step that only types that slot (`type_text` / `browser_type` / `browser_fill` whose text is exactly `{slot}`, no `submit:true`); a later step that types it pauses again. A step that uses the slot any other way is not skipped: the run pauses with `paused_reason:"on_page_not_skippable"` (`paused_detail` says why). `page:{slot:false}` undoes a mark. `waiting.slots[i]` carries `on_page`, `on_page_refused` (the mark was just spent) and `vault_failed`. Refused: `slot_via_vault`, `bad_page`. A value and a mark for the same slot in one call → the value wins. Over HTTP: `POST /control/replay/input {run_id, inputs?, page}`.

**Remember a password — `remember`:** `playbook_replay({run_id, inputs:{secret_1:"…"}, remember:{secret_1:true}})` (also with `task` + `args` at start, or `POST /control/replay/input {run_id, inputs, remember}`) saves the value of a private slot, given in that same call, encrypted for this Windows user (not in the macro, an export, a log or a result). Later runs type it by themselves, for the same macro, slot and place (the site's host or the program's exe). It goes by itself once the previous run that used it was confirmed (ended well and the screen where it was typed no longer exists); otherwise the next run asks again with `waiting.slots[i].remembered_rejected:true`, and what you give then replaces it. `remember:{slot:false}` forgets it. `waiting.slots[i]` carries `can_remember` and `remember_store`; the run state carries `remembered:{used,saved,failed}`. Errors: `remember_needs_value`, `remember_not_secret`, `remember_unavailable`, `bad_remember`. After the first run, do not ask the person again.

## 8. Vault bridge — a vault value reaches the run without passing through you
1. `playbook_replay({task})` without the value → it pauses. Each `waiting.slots[i]` has `env` (e.g. `VERDESK_SECRET_1_PASSWORD`) and, if the macro was linked, `vault:{module_id, line, env:[{name, module_id, line}]}` — that `env` goes to `vault_run` as is. `waiting.control_port` and `waiting.run_no` are the script's two arguments (both numeric).
2. Not linked? `vault_list` → pick the block → `playbook_annotate({task, vault:{secret_1:{module_id, line}}})` once. It saves where the value is; a link that stops existing (vault changed, other project) just makes `vault_run` say so.
3. `playbook_replay({run_id, vault:["secret_1"]})` — returns at once; the run window says "asked the vault" and shows no field. `vault:[]` gives the slots back to the person (do it if `vault_run` fails).
4. `vault_run({script:"scripts/verdesk-vault-bridge.ps1", args:["<control_port>","<run_no>"], env:[…the vault.env of every waiting slot…], timeout_sec:120})` → `run_id`; follow with `vault_run_status`. The script posts the values, with the run number, to `127.0.0.1:<control_port>/control/replay/input` (this machine only, not MCP) and prints one status line, never a value. When nothing is missing the run goes on by itself. A late delivery (the person took long to approve the script) still fills the same run while it waits; if that run was stopped and another started, Verdesk refuses it (`not_active`) and nothing is typed.
5. Exit codes: 0 delivered (the line says `filled` and `still missing`: a field the person must type is not an error); 2 no port, no run number or no `VERDESK_*` variable; 3 Verdesk did not answer; 4 Verdesk refused (`no_run`, `not_active`, `unknown_slot`, `too_long`). Read the line, then `playbook_replay({run_id})`.

Write this file once, exactly (PowerShell 7, UTF-8 without BOM; `vault_run` only runs project scripts and the person approves it once in CleverCoder):

```powershell
# scripts/verdesk-vault-bridge.ps1 - run by vault_run with args = [Verdesk control port, run number] and VERDESK_<SLOT>_<PASSWORD|USER|...>
# variables in its environment. Hands them to the macro run that asked for them (run number), never to another. Talks only to 127.0.0.1; never prints a value.
$ErrorActionPreference = 'Stop'
if ($args.Count -lt 2 -or $args[0] -notmatch '^[0-9]{2,5}$' -or $args[1] -notmatch '^[0-9]{1,18}$') { Write-Output 'missing control port or run number (two numeric arguments)'; exit 2 }
$inputs = @{}
foreach ($v in Get-ChildItem Env:) { if ($v.Name -match '^VERDESK_(.+)_(PASSWORD|USER|USERNAME|TOKEN|KEY|SECRET)$') { $inputs[$Matches[1]] = $v.Value } }
if ($inputs.Count -eq 0) { Write-Output 'no VERDESK_* variable arrived'; exit 2 }
$body = @{ run_no = [int64]$args[1]; inputs = $inputs } | ConvertTo-Json -Compress
try {
    $r = Invoke-WebRequest -Uri "http://127.0.0.1:$($args[0])/control/replay/input" -Method Post -ContentType 'application/json; charset=utf-8' `
        -Body ([Text.Encoding]::UTF8.GetBytes($body)) -UseBasicParsing -TimeoutSec 30 -SkipHttpErrorCheck
} catch { Write-Output ('Verdesk did not answer: ' + $_.Exception.Message.Split("`n")[0]); exit 3 }
$j = $null
try { $j = [string]$r.Content | ConvertFrom-Json } catch { }
if ($r.StatusCode -ge 400 -or $null -eq $j -or $j.ok -ne $true) {
    $why = if ($j -and $j.error) { [string]$j.error + $(if ($j.slot) { ' ' + [string]$j.slot } else { '' }) } else { 'HTTP ' + [int]$r.StatusCode }
    Write-Output ('Verdesk refused: ' + $why); exit 4
}
Write-Output ('filled: ' + (@($j.filled) -join ',') + '; still missing: ' + $(if (@($j.still_missing).Count) { @($j.still_missing) -join ',' } else { 'none' }))
exit 0
```

## 9. Drafts (Pro) — what Verdesk recorded on its own
While you work through Verdesk tools it keeps a **draft** of your route per site or app and agent. It closes when the site or app changes, after 600 s without actions, or at 200 steps (under 2 steps is discarded). It needs Pro and the person's recording switch on, and it only records calls made through Verdesk tools, not the person's own keyboard or mouse. Drafts stay on this computer; the person reviews and deletes them in the Macros tab of the app.
- **Find them.** Arriving at a site or app (after `navigate`, `go`, `set_view_target`, `focus_window` or `browser_select_tab`) Verdesk adds one line to the response, once per agent + scope per server session, nothing if there are none: `Verdesk: 2 drafts + 1 macro for sii.cl - playbook_list({scope:"sii.cl"})` (verbs surface: `remember({op:"list",scope:"sii.cl"})`). Read one with `playbook_recall({task, include_steps:true})`.
- **A draft is a guide, not a macro.** `status:"draft"` = not yet reviewed, not replayable until promoted. A step with `not_replayable:true` uses a tool the replay does not repeat (`browser_drag`, `browser_upload`, `reload`, `back`, `forward`…): a replay would stop there; the signature's `not_replayable_steps` counts them. `navigate`, `browser_click`, `browser_fill`, `browser_type` and `browser_transfer` do replay by the element (section 4); a `{hole}` inside a `navigate` URL is percent-encoded. A step may carry a `locator` (url, title, process, `dom` {selector, role, name, context, text}, `uia`, text_around, `rel`, `crop`): the signals to find its target again.
- **Private values stay out.** A value Verdesk recognizes as private is saved as `{secret_N}` with `secret:true` (no crop, no nearby text); in a draft, a field it cannot classify is masked too. Recognition is best on password fields; for any other private value, use a slot.

## 10. Objects — the Pixel Match book (Pro)
Teach a button by its pixel fingerprint and find it again anywhere — useful where UIA falls short (games, custom UIs, WebView).
- `learn_button({label, x, y, w, h, app?})` — fingerprint a bbox (a uniform region is refused: include the glyph).
- `find_button({label})` → `{found, x, y, rect, match_pct, candidates}` or `{found:false}`. Not found = not on this surface, off the viewport, or its look changed: `look()` again, `object_thumbnail` to recall its shape, learn it again, or `click_text` if it has text.
- `click_button({label})` — find + click; the visual action macros record. On replay it resolves the object by its exact recorded name (a renamed or deleted object fails the step instead of clicking a lookalike). It clicks when one place wins clearly: two places that match about equally end in an `ambiguous` error listing them, with no click — and an object's backup images (variants) all count, so two copies that look different are still two places. `find_button` reports only the first fingerprint that matches, so it can show one candidate where `click_button` says ambiguous.
- `track_object({label})` → `{found, moved, dx, dy, searched}` · `object_thumbnail({label})` → 48px sample · `list_buttons()` · `delete_button({label})`.
- **Links** (deterministic, from `playbooks.json` + `buttons.json`): `object_links()` → `{objects:[{label, registered?, app, trains, last_seen_rect}], orphan_refs, unused}` · `objects_used_by_train({task})` · `trains_using_object({label})` (move or relearn an object → see the macros it affects).

## 11. Run commands on this machine (two tools)
- `open_run({command})` — opens the Windows Run dialog (Win+R), types, Enter. Visible, desktop target only (on the browser it answers `error_type:"wrong_target"` and sends no keys). For GUI apps (`mspaint`), terminals (`cmd`/`powershell`/`wt`) or a `cmd /c …` one-liner that closes itself. After opening a terminal, drive it with `type_text` + `press_key({key:"Enter"})`.
- `run_command({command, cwd?, detach?, timeout_ms?})` — runs locally via `cmd /C` and returns `{stdout, stderr, exit_code, timed_out, duration_ms}` (`timeout_ms` default 30000). `detach:true` launches a GUI or long-running process and returns at once. On by default; if the person turned off Settings → "Allow run_command", it answers with an error: ask them to turn it on, or use `open_run`. Macros classify it `irreversible` (a command cannot be undone).
